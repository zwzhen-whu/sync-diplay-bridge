# CarPlay 通话音量修正 2.1.1

本车为 MEK-MX8Q / Android 8.1，使用原签名 DiPlay 0.2.21 / code 40。

## 实车诊断

- 原状：音量键将 `STREAM_VOICE_CALL` 从 12 调至 4 再升高，通话音频仍无可感知变化；媒体音量维持 5。
- 打开 DiPlay 的音频焦点后，车机确实授予 `AUDIO_SOURCE_BT_PHONE / PRIORITY_TELEPHONY_SERVICE`，用户仍确认通话音量不变。
- 临时将媒体音量 4 降至 2、再恢复 4，用户确认通话声音仍未改变。因此没有实现通话与媒体音量联动。
- 对 `telephony` 下行 PCM 临时施加 0.1 增益，用户确认能够听到明显降低和恢复。
- 临时测试结束时，在仍可能执行的 ART 方法上卸载钩子，紧接着 DiPlay 音频线程 SIGSEGV、CarPlay 断连。此撤销过程是主要嫌疑，但 tombstone 未提供完整的符号化调用链。临时脚本和 DEX 已删除；DiPlay 换 PID 后恢复连接。

## 修正实现

新增独立的“修正 CarPlay 通话音量调节”开关，默认关闭。

- 音频处理器在一个 DiPlay 进程中只安装一次，保留至该进程结束。
- 开关关闭、桥接停止或 15 秒控制租约过期时直接旁路处理，不动态卸载方法钩子。
- 仅对 `AudioRenderer` 的 `audioType=telephony` 下行 PCM16 施加增益。音乐、导航、Siri、麦克风、编码和 USB 连接不在处理范围内。
- 增益为系统通话音量除以该流的最大音量，限于 0–1；静音或音量 0 为零，最高档为原始音量。没有额外放大或削波，也不改媒体音量及用户的通话音量设定。
- Java 处理只改当前写入区间内的样本。配置读取、音量查询和状态写入在独立定时任务中执行。
- 单独的本机辅助接口校验 Android 8.1、原版 DiPlay 版本和签名、桥接签名、进程 UID/PID/启动时刻及运行资产散列。
- 不完整注入后禁止在同一个进程再次注入；需重开 DiPlay。辅助接口不接受自由命令，不读写联系人、配对数据或录音。
- 与地图处理器使用独立文件和报告；原地图脚本不变。两项处理器启动通过文件锁串行执行。配置文件恢复正常的应用数据安全标签，系统保持 SELinux Enforcing。

## 验证边界

构建和离线回归已通过。PCM 样本、边界、静音、范围和控制租约已有纯 Java 检查；2026-10-25 覆盖安装 2.1.1 后，用户确认普通电话的音量加减生效，挂断后连接正常；处理计数 2978，原生进程 PID/启动时刻在测试前后保持一致且无运行错误。原桥接与地图设置已核对保留。后续微信修复另行验证。

## 微信与语音输入

此版本不宣称修复微信麦克风。本次用户确认 Siri 和微信文字框语音输入正常，而微信通话、语音消息、地图语音搜索和键盘听写失败。失败片段中 DiPlay 仍有有效幅度和发送计数；这些记录不证明 iPhone 或微信最终接受了音频。

官方同类报告仍未解决，见 [#718](https://github.com/shihabal3amri/DiPlay/issues/718)、[#1017](https://github.com/shihabal3amri/DiPlay/issues/1017)、[#1040](https://github.com/shihabal3amri/DiPlay/issues/1040)。USB / 无线对照，以及车机电话音频设置，是尚待本车验证的方向，不能当作已验证修复。
