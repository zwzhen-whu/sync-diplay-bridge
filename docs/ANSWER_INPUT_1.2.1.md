# 1.2.1 接听键直接投递

2026-10-23。包名保持 com.local.diplay.clusterbridge，versionName 1.2.1，versionCode 21，沿用原签名。

## 已有证据

用户反馈：1.2 仪表拒接可以执行，仪表接听和上一曲接听不能接通。新一次用户测试时，桥接状态为 DiPlay 来电中，近期按键结果未确认，采集未见 DiPlay-CallKeys 接听回执。只能确认失败在接听入口或投递路径，不能认定 DiPlay 已接受后仍无法控制 iPhone。

只读检查确认：当前 CarPlayHostActivity 取得焦点，窗口格式解析通过；本机 android.hardware.input.IInputManager.injectInputEvent(InputEvent,int) 接口存在。未在探针中调用该注入方法。

旧实现用独立 /system/bin/input 进程发送按键，1000 毫秒就销毁超时进程。实车只运行无参数帮助、不发送任何按键，三次耗时为 1081、628、789 毫秒（含 ADB 往返）。该预算不足是明确风险，但当时没有逐阶段错误码，尚不能将它认定为每次失败的唯一原因。

## 修改

接听仍严格依据 DiPlay 当前 iPhone 来电状态，仍为上一曲接听、下一曲拒接／挂断。发送前再次核对进程、通话身份、阶段、开关、有效期、前台和输入焦点。

由常驻 root 辅助组件直接取得系统输入 Binder，投递 SOURCE_KEYBOARD 的 313 键，按下／释放各一次。采用异步系统投递，避免等待其他无障碍服务导致命令启动或等待超时；系统接受排队不等于 DiPlay 或 iPhone 接听成功。即使按下返回不确定或抛异常，也只清理释放一次，不重发整次按键、不尝试 CALL(5) 或其他入口。

仅新收到的 DiPlay 自身、同进程、同键码接听回执才表示 DiPlay 接受请求。界面区分：CarPlay 非前台、输入焦点不符或检查超时、系统投递未确认、缺少 DiPlay 回执、DiPlay 收到但未接受，以及状态已变化。仪表菜单和 Key Mapper 使用相同实现和错误提示。

不改变拒接／挂断的定向广播路径、普通切歌、蓝牙设置和仪表显示。没有新增 Android 权限。所有电话操作仍只因用户按键或仪表确认操作触发。

## 验证边界

离线回归检查按下／释放顺序、失败后释放、禁止自动重发和回退、各阶段错误保持、DiPlay 状态校验及旧导航／蓝牙行为。APK 构建和原签名验证见 validation.json。原始通话和窗口数据仅保留本机私有排查目录，不进入交付源码、安装包或 GitHub。

电话接通和仪表接听必须实车验证。`sent=true` 仅表示 DiPlay 接受并排队，不等于手机已接通。
