# 0.1.9 本地排查记录

日期：2026-10-17。基于已发布的 v0.1.8，修复在 `codex/local-startup-road-audit` 分支完成。初始排查阶段无法连接车机，先完成本地回归及构建；随后已在原测试车机覆盖安装并完成 Android 车机重启后的首次连接测试，见[实车测试记录](VEHICLE_TEST_0.1.9.md)。0.1.9 发布采用同一份实测安装包。

## 开机显示已连接但停在 DiPlay 主页

### DiPlay 本体的启动入口差异

已核对本地保存的 DiPlay 0.2.19 APK，而不只是参考公开源码：

1. `BootReceiver.onReceive` 在开启开机启动时，直接启动 `DiPlayActivity`，标志为 `0x34000000`（NEW_TASK / CLEAR_TOP / SINGLE_TOP），没有设置 MAIN action 或 LAUNCHER category。
2. `DiPlayActivity.onCreate` 和 `onNewIntent` 中，“已有会话就打开 CarPlay”受 `isLauncherIntent` 限制；该函数要求 MAIN + LAUNCHER 且没有 `page` extra。因此开机广播的 Intent 不进入这条分支。
3. 回到主页后的初次 `onResume` 自动连接又要求当前没有会话。若 USB 已经建立会话，则不会触发；主页仍按会话状态显示“已连接”。

由此存在一条可解释症状的路径：USB 先启动 CarPlay，稍后的开机广播再把主页带到前台；会话仍活着，但 UI 留在主页。历史车机日志记录了先启动 USB CarPlayHostActivity，约 10.2 秒后由 DiPlay UID 发出不带 action 的 `0x34000000` 主页启动，与该入口一致。随后本车重启测试又记录到同样的启动顺序及 CarPlay → 主页 → CarPlay 的前台变化，自动恢复发生在桥接请求之后；参见实车记录。本次仍只覆盖一次 Android 车机重启，不能据此排除所有回退原因。

本次仍遵守独立桥接方案，没有修改 DiPlay APK。下述 90 秒有界恢复处理的是这一类入口回退；若将来修改 DiPlay 本体，根修方向应是让开机入口正确处理已有会话，避免再次把有效 CarPlay 会话留在主页。

### 桥接补救逻辑的缺口

旧版将一次点击请求当作本轮已完成，不能处理点击未打开、打开后再次回退；默认 30 秒窗口也无法覆盖更晚的启动回退。开机桌面或其他 Activity 短暂前台还会直接终止本轮检查。开关关闭、使用情况权限缺失期间仍记录连接起点，晚些启用时可能早已过期。

已改为：有效启用且可读前台时建立 90 秒窗口；只在准确识别为 DiPlay 入口并稳定约 2 秒后调用原小组件点击动作。最多 3 次，间隔至少 8 秒。其他页面只暂停候选计时；不在其他应用前台拉起 CarPlay。看到播放器连续 10 秒后确认页面，但不提前停止窗口内的回退检查。连接断开会重置本轮状态。

这仍是外部桥接补救，没有修改 DiPlay 的内部启动竞态。入口和设置共用 Activity，窗口内进入设置仍可能被补跳转，需要留在设置时应关闭此功能。90 秒后或三次耗尽不继续请求。Android 后台界面启动限制、前台事件缺失及原车休眠/唤醒策略需要实测。

## 百度路名为何可能因用户而异

本车历史记录中的百度地图没有专用路名字段，但导航说明含道路文字。其他手机、地图或 DiPlay 版本不一定输出完全相同的诊断字段或同样完整的记录。

| 检查项 | v0.1.8 的缺口 | 本次处理 |
| --- | --- | --- |
| 多个转向编号 | 只接受 u16 单值，遇到列表丢弃路线 | 按 DiPlay 协议取 u16 列表的第一个，支持完整十六进制预览及具名列表；截断/奇数字节拒绝 |
| 分批更新 | 忽略缺状态的距离更新；有状态而缺编号/距离会清空路线 | 只在同进程、同会话、已存在且未过期的活动路线内保留未更新字段；结束后不可恢复 |
| 字段名称 | 强制要求诊断标签叫 `param` | 按数字参数 ID 读取，兼容格式化器的具名字段 |
| 转向详情晚到 | 详情时间晚于路线时直接拒绝路名 | 同编号、方向和距离匹配时接受后来到达的说明 |
| 首个路口乱序 | 第 0 个转向详情晚到会把刚收到的活动路线及后续路口缓存清掉 | 已确认当前活动编号为 0 时按详情更新处理，保留有效路线及已收到的后续路口 |
| 转义文本 | 拒绝 `\t` / `\n` / `\r` | 转为空格，保留实际文字 |
| 当前道路字段 | 未作为日志回退来源 | 在转向匹配且下一道路为空时使用同一活动路线中的真实当前道路 |
| 跨开机缓存 | 只核对 UID，PID 在另一次开机可能复用 | 增加系统开机编号校验；读不到编号则不恢复磁盘缓存 |
| 时钟回拨 | 旧时间戳阻止较早的新状态进入 | 清除不再有效的路名及前台缓存，等待新状态 |

所有回退仍检查 DiPlay UID、进程/会话、当前转向、方向、距离以及 15 秒状态时效；没有按文字猜道路，也没有放开导航的 5 秒超时。可信会话关闭会清除对应缓存。未知数据仍显示“道路名称未提供”。

## 日志权限与诊断

旧版仅看到 READ_LOGS 已授予就显示“正在读取”，这并不证明读到了 DiPlay 日志。旧 Android 若是在桥接进程启动后授权，进程可能没有日志组。本次为 Android 8/9 增加当前进程组检查；能读取 proc 且明确缺组时建议“强行停止后重新打开桥接”，同时仍尝试读取，避免把标准固件的组检查当作所有定制固件的绝对条件。部分固件无法读取 proc 时仍尝试正常日志路径，不据此拒绝转发。

状态现在区分“尚未收到 DiPlay 导航记录”和“收到导航帧 X，解析成功 Y”。因此其他用户缺路名时，应先核对桥接及 DiPlay 版本、日志权限状态、是否收到/解析到帧，以及是否重新开始过导航。没有用户那边的记录，不能断言本次修复就是其具体原因。

未授权、系统禁止读取、DiPlay 没有输出诊断或旧说明已被日志缓冲覆盖时，本应用无法凭空恢复路名。重启桥接不等于 iPhone 会重发所有旧说明，必要时须等新的转向说明或重新开始路线。

## 顺带发现并防护的问题

- 小组件视图已建立但 `startListening()` 抛异常时，旧版保留非空视图，导致后台不再重试；现在清理失败实例并回到重试路径。旧宿主的迟到回调通过实例代次丢弃。
- 日志线程与停止/清理可能交错，停止后仍写缓存或发回调；现在对解析、缓存及回调提交与停止操作串行处理，并合并待处理回调。
- 增加繁体“公尺”、俄乌语米/公里及双向文字标记的距离解析，避免有效导航被误判为距离未知。

小组件异常和线程防护属于静态排查后的修复，已通过 Android 编译；尚未在真实 Binder 故障、固件进程回收或并发调度中验证。

## 本地验证范围

将相同复现程序分别链接 v0.1.8 标签源码和当前源码，比较开机桌面中断、点击后重试、晚回退、具名字段、多个编号、转义制表符、分批距离更新、后到说明、时间回拨及繁体距离这 10 个场景。旧版失败的输入在当前实现中得到预期输出。原有五组回归继续运行，新增一组审计回归；覆盖重复歌曲不重发、次数/间隔/窗口边界、其他应用不跳转、路线结束不可复活、错误 UID/进程/方向/距离不能套用路名等。

复现输入是基于本地 DiPlay 协议解析器及诊断格式化器构造的离线场景，不是其他用户上传的故障日志。历史车机日志用于核对格式和已观察的启动时序；后续实车测试另外验证了本车 Android 重启后的首次连接、主页恢复和百度路名显示。整车断电冷启动、其他用户百度地图路名、其他固件后台启动限制、林肯显示及休眠恢复仍需实测。

公开接口依据：[Android UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager)、[DiPlay 转向解析](https://github.com/shihabal3amri/DiPlay/blob/0919997b8645b825e4370866d66d455678d2b9da/shared/src/main/java/com/shilapi/xcertplay/hud/BydHudRouteState.kt)、[DiPlay 诊断格式化](https://github.com/shihabal3amri/DiPlay/blob/0919997b8645b825e4370866d66d455678d2b9da/shared/src/main/java/com/shilapi/xcertplay/iap2/trace/Iap2FrameFormatter.kt)。
